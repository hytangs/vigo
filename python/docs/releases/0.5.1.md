# VIGO Python 0.5.1

Turn Route and Matrix outputs into analysis tables with two incremental Result accessors:

- `iter_journeys()` retains one summary per journey or Matrix row, including blocked outcomes and rows without itinerary detail.
- `iter_legs(include_geometry=False)` returns individual legs with journey, scenario and origin–destination identifiers. Matrix queries must request `include_journeys=True` to supply legs.

Blocked plan objects retain their explanation without being counted as available journeys.

Returned records are independently mutable and preserve Engine field names and units. Geometry is omitted before copying by default. A runnable [CSV export example](../../examples/decompose_result.py) and [pandas recipe](../guide.md#decompose-journeys-for-analysis) support downstream analysis.

Python 3.10+ and Engine 0.5 remain supported; API and City/Result schemas are unchanged. Existing 0.5 Cities do not need rebuilding. The new standalone Engine timetable cache is a Rust runtime feature; the Python wrapper continues to use its existing resident CLI protocol.

## Resident processes and incremental export

`Result.export_tables()` writes journey and leg CSVs plus provenance with bounded additional memory. Empty tables retain their respective column headers. All files are serialized before replacement, preserving existing exports if serialization fails. The example delegates to this method.

When the Engine advertises `output.requestServiceDate`, Python reuses idle resident CLI processes across dates and starts extra processes only for overlapping queries. Earlier 0.5 engines keep the compatible date-specific behavior. The Node CLI continues to own its native-kernel and prepared-network caches; this change does not substitute the standalone Rust result protocol.

Repeated Matrix endpoints reuse journey reconstruction in Engine 0.5.1, including optional geometry. Requested row order and origin–destination identifiers are preserved, and returned records remain independently mutable.
