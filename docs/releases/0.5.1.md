# VIGO 0.5.1

## Reuse prepared service dates

The standalone Rust runtime retains prepared scheduled timetables when queries switch dates. Returning to a retained date and transfer policy reuses its arrays and indexes, while routing search and its shared query workspace remain unchanged.

Each City retains up to eight inactive timetables within a default 128 MiB budget. Set `VIGO_TIMETABLE_CACHE_BYTES` to tune the budget, or `0` to disable retention. Least recently used entries are evicted; oversized timetables and realtime snapshots are not retained. The budget is additional to the active timetable and allows the selected scenario to borrow unused capacity in a scenario collection; separate workers retain separate budgets.

`memory.timetableCache` exposes retention, hits and evictions. See the [standalone guide](../guides/rust-standalone.md) for accounting and configuration.

## Compatibility

Published 0.5 Cities open without rebuilding. API 1.0, City format 1 and Result schema 1 are unchanged. The [permanent prepared-data contract](../reference/format-0.5.0.md) remains the compatibility baseline.

## Reduce preparation and output overhead

First-date preparation reads timetable rows in trip order and restores service-date order with compact trip blocks. This avoids a whole-timetable SQL sort while preserving connection order, boarding permissions and overnight service. Existing Cities need no rebuild or additional disk index.

Timetable indexing borrows source columns instead of duplicating them. Reach reuses raster-crossing scratch across edges while preserving exact grid coverage. Matrix materialization reuses bounded trip metadata within a request. Departure and arrival windows compute candidate ranking and duplicate-detection keys once per selection pass, preserving journey order and alternatives. Linux retains allocator pages on date-cache hits unless preparation or cache eviction released data.

The resident CLI advertises per-request service dates for Python process reuse. Date changes reuse the loaded street network and select a retained timetable. Its service-context cache retains up to four contexts by default within the existing byte budget; `VIGO_ACTIVE_KERNEL_CONTEXT_CACHE_MAX_ENTRIES` remains configurable. HTTP scheduling reclaims expired and canceled queued requests before dispatch without consuming the short-query fairness allowance.

## Calendar views and matrix reuse

Calendar weekday masks and dated exceptions are indexed once per City. Equal immutable timetable columns share storage across retained dates, while each date keeps its scan indexes. Collection cache capacity follows demand within the existing total byte budget.

Transit Matrix reuses repeated OD pairs through direct walking and geometry reconstruction, then restores the requested output order. Trace diagnostics report the requested and distinct pair counts.

The Node CLI also reuses repeated journey materialization, including direct-walk geometry. Its request-local cache is bounded to 2,048 pairs and a 1 MiB key-storage estimate. Returned journeys are independent copies; diagnostics expose materialized and reused journey counts.

## Studio responsiveness

Queued point queries, including departure-window alternatives, take priority over analytical work, with at most four bypasses before the oldest analytical job runs. Preparation order and running queries are preserved; existing worker and memory limits still apply.

Reach point inspection applies the map’s walking limit, keeping the selected journey consistent with the accessibility query.
